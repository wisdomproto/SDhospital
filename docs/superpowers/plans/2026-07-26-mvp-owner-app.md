# Plan 06 — 보호자 앱 MVP

- 작성일: 2026-07-26
- 스펙: `docs/proposal/2026-07-26-sd-platform-proposal.md`
- 목표: **보호자가 매 진료마다 리포트를 받고, 실제로 열어보는지 숫자로 확인한다.**
  통과하면 1차병원 EMR·PACS·AI로 확장하고, 미달이면 확장하지 않는다.

## 전제

- SD는 **기존 EMR을 계속 쓴다.** 이 시스템은 EMR 대체가 아니라 **보호자·1차병원에게 보여줄 것만 담는 공유 레이어**.
- 데이터는 당분간 **수의사가 직접 입력**한다 (기존 EMR 연동 없음).
  → 최대 리스크는 "몇 달 뒤 입력이 조용히 끊기는 것". 입력 화면에 보호자 앱과 동급 공수를 배정한다.
- 기본 단위는 **진료 회차**. 입원하러 온 환자도 진료 기록이 먼저 생기고, 입원은 그 회차에 딸린 별도 기록.

## 완료분 상세

### M-0 — 입원을 회차 하위로 (`0007_admission_under_visit.sql`)
24개 파일이 `admission.patient_id`를 쓰고 있어 전부 조인으로 바꾸는 대신,
`patient_id`를 남기고 **복합 FK `(visit_id, patient_id) → visit(id, patient_id)`** 로 묶었다.
입원의 환자가 회차의 환자와 어긋나는 것이 DB 차원에서 불가능하고, 기존 조회·RLS는 그대로 동작한다.
입원 생성은 **회차 화면에서만** 한다 (환자 화면의 입원 등록 폼 제거).

### M-1 — 회차 리포트 (`0008_visit_report.sql`)
리포트는 회차당 1건이므로 별도 테이블 없이 `visit` 컬럼 3개
(`report_comment`, `report_sent_at`, `report_read_at`).
보호자는 `visit`에 쓰기 권한이 없으므로 열람 표시는 **DEFINER 함수** `mark_visit_report_read`로만.
본인 반려동물 + 발송된 리포트 + 최초 1회 조건이 함수 안에 있다.

### M-1b — 입원 일일 리포트 + 진료 종료 (`0009_admission_report.sql`)
`admission_report` 테이블, `unique (admission_id, report_date)`로 하루 1건 보장.
사진·바이털은 복사하지 않고 `report_date` 기준으로 그날 것을 조립한다.
`visit.closed_at` 추가 — 리포트를 보내면 종료도 함께 찍어 버튼을 하나 줄였다.

### M-2 — 오늘 할 일 (`/today`, `src/lib/worklist.ts`)
- 진료 리포트: `closed_at is not null` AND `report_sent_at is null` (밀린 것 포함)
- 입원 리포트: `status='admitted'` AND 오늘자 미발송
- **입원은 지난 날짜를 밀린 것으로 세지 않는다** — 3일 전 경과를 되돌아가 쓸 수 없고, 그러면 목록이 영영 안 비워진다.

## 보호자에게 무엇을 보여줄 것인가 (2026-07-28 결정)

**원장 지시: 상세 처방 데이터는 보호자에게 주면 안 된다 — 분쟁거리가 된다.**
"어떤 문제로 왔고, 어떤 검사를 했고, 어떤 치료를 받았다" 수준으로 준다.

| 보호자에게 | 차단 |
|---|---|
| 담당의 코멘트 (`visit.report_comment`) | 진료 내용 원문 (`visit.note`) — 의료진 기록·축약어 |
| 진행한 검사 요약 (영상 modality 자동 집계) | **처방 상세** (약품·용량·용법·기간) |
| 사진·영상, 입원 일일 경과 | 입원 경과 메모 (`admission.note`) |

- 보호자 쿼리에서 `note` 컬럼 자체를 뺐다 — 실수로 다시 새어나갈 여지를 없앴다.
- 1차병원(`/referral`) 화면은 **그대로 전부** 보여준다. 의료진이다.
- `visit.note` 는 SOAP 틀 버튼으로 마음껏 쓰면 된다. 보호자에게 안 나간다.

## 사진 · PWA (2026-07-28)

- **업로드 전 브라우저에서 축소.** 1600px + WebP, `canvas.toBlob` — 서버 변환·라이브러리 0.
  업로드 자체가 빨라져 병동 입력이 안 끊긴다. 실패하면 원본을 그대로 올린다.
- **의료영상만 예외**: 원본은 판독용이라 보존하고 보호자용 사본(`medical_image.preview_path`)을 함께 올린다.
  보호자 화면에 "원본 받기" 링크. DICOM 은 캔버스가 못 읽어 사본을 만들지 않는다.
- **서비스워커는 진료 기록을 캐시하지 않는다.** 가족 공용 폰·로그아웃 후 잔존·오래된 리포트 노출 때문.
  껍데기(아이콘·오프라인 안내)만 캐시한다.
- `sw.js`/`offline.html`/`manifest.webmanifest` 는 프록시 인증 가드에서 제외해야 한다
  (서비스워커가 로그인 HTML 을 받으면 등록이 실패한다).

## M-5 전자 동의서 (`0011_consent.sql`)

- **양식 본문은 코드**(`src/lib/consent/forms.ts`)에. git 이 곧 버전 관리다. DB 에는 서명 결과만.
- **양식 5종** — 입원 / 수술·마취·검사 / 투석(CRRT) / 재활 / 퇴원요청.
  슬개골탈구·장생검은 **같은 수술 양식 하나**다. 진단·처치·시술설명만 발행 시 채운다.
- ★ **서명 시점의 본문 전문을 `body_snapshot` 에 박는다.** 나중에 양식 문구를 고쳐도
  과거 서명은 그때 읽은 문장을 보존한다 — 증빙에서 중요한 건 서명 그림이 아니라 무엇에 동의했는지다.
- 서명 캔버스는 **포인터 이벤트, 라이브러리 0**. 손가락·스타일러스·마우스가 같은 코드.
  결과는 투명 PNG data URL 로 행에 저장 (보호자는 Storage 쓰기 권한이 없고, 증빙은 기록과 붙어 있어야 한다).
- 서명은 **DEFINER 함수 `sign_consent`** 로만. 본인 반려동물 + 미서명 조건이 함수 안에 있어 두 번 서명이 불가능하다.
- 화면 하나(`ConsentSheet`)를 보호자 앱·병원 태블릿·직원 열람이 공유한다.
  발행하면 보호자 홈에 "서명이 필요합니다" 배너가 뜨고, 태블릿은 목록의 [서명받기]로 연다.
- **주민등록번호 13자리 전체를 받는다**(원장 결정). AES-256-GCM 암호화 후 저장, 화면은 마스킹.
  ⚠️ **`CONSENT_ENC_KEY` 를 잃으면 복구 불가.** Railway 에 별도 값으로 넣고 백업해야 한다.

## 레퍼럴 브릿지 (`0012_referral_bridge.sql`, 2026-07-29)

MVP의 나머지 절반. 1차병원이 **돌려받는 것**이 없으면 의뢰가 늘 이유도 없다.

- **진행 상태는 저장하지 않는다.** 이미 있는 사실에서 전부 파생된다 —
  `closed_at`(진료중/종료) + `admission.status`(입원중/퇴원) + `referred_back_at`(환송).
  저장하면 실제 상태와 어긋나는 순간이 오고 그걸 맞추는 코드를 또 짜야 한다.
  유일하게 파생 불가능한 "환송했는가"만 컬럼으로 둔다 (`src/lib/referral.ts`).
- **환송 소견서**는 회신 요약이지 기록 사본이 아니다. 원장은 진료 원문·처방을 이미 다 본다.
- **레퍼 대시보드는 새 페이지를 만들지 않고 `/hospitals`에 붙였다.** 답해야 할 질문이
  "누굴 만나러 가야 하나" 하나라서, 총건수보다 **최근 90일 vs 직전 90일**과 이탈 여부를 보여준다.
  `의뢰 끊김`(최근 90일 0인데 그 전엔 있었음) · `미환송 N`(진료 종료됐는데 회신 안 함).
- **접근 로그** — 외부 역할은 `log_access` DEFINER 로 **남길 수만** 있고 읽지도 고치지도 못한다.
  로그 자체가 감사 대상이라 열람자에게 보여주지 않는다. 직원은 환자 화면에서 최근 20건을 본다.
  RLS 테스트로 직접 insert 차단·역할 기록 정확성을 확인했다.

## 보호자 리포트 조립 + 전송 미리보기 (`0013_visit_chief_complaint.sql`, 2026-07-29)

레퍼런스(타 제품 weVoice)와 같은 형태를 목표로 하되 **요약은 하지 않는다.**
진료 원문을 우리가 줄여 내보내면 그 문장의 책임을 병원이 진다.

- 수의사가 넣는 값은 셋뿐 — **주 증상(C.C.) 한 줄 · 담당의 코멘트 · (선택) 추가 안내.**
  제목·프로필(종·품종·나이·체중)·"지난 방문 대비 변화"는 전부 기계적으로 조립한다.
- **변화 = 직전 회차 C.C. + 체중 증감.** AI 없이 만들 수 있는 유일한 정직한 비교이고,
  실제로 보호자가 가장 궁금해하는 두 가지다. 체중은 0.005kg 미만 차이를 변화로 말하지 않는다.
- 코멘트는 **한 줄 = 항목 하나**. 글머리표는 지운다.
- `buildOwnerReport()`는 순수 함수 — 포털은 서버에서, 미리보기는 **폼에 입력 중인 값으로**
  클라이언트에서 같은 함수를 돌린다. 그래서 미리보기가 곧 실제 발송물이다.
- 미리보기는 네이티브 `<dialog>`. 코멘트가 비면 전송 버튼이 잠긴다.
- 회차 화면과 병동 입력 화면 둘 다에 붙였다.

## 시연용 데이터 (`supabase/seed/demo_history.sql`, 2026-07-29)

"지난 방문 대비 변화"가 이 제품의 핵심인데 데모 환자가 전부 1회차라 한 번도 뜨지 않았다.

- 환자별 **질환 스토리**(주 증상 배열·코멘트 배열·체중 시작/끝·방문 횟수)만 적고 DB가 펼친다.
  236건을 손으로 쓰면 중간에 그만두게 된다.
- 문장은 길이가 다른 배열(8·7·6개)로 돌려 조합을 흩뜨렸다 — 같은 주기로 돌면 목록에서 복붙처럼 보인다.

## 보호자 질문 응대 — AI 아니라 FAQ부터 (2026-07-28 결정)

AI 채팅 대신 **병원이 미리 써 둔 답변**을 조건에 맞춰 띄운다.
이유는 비용보다 **책임**: AI가 잘못 답하면 병원 책임이 되지만, 수의사가 검수한 문장만 나가면 그 리스크가 없다.

- **직원용 관리 화면 필수.** 문구 수정에 개발자를 불러야 하면 갱신이 멈춘다.
- **재료: 원장 보유 10년치 상담 대화 기록** (제공 약속, 미수령).
- 한계: 개별 수치 질문("신장 수치가 왜 올랐나요")은 못 답한다 → 전화로 온다.

## 알림 — 웹 푸시 (`0015`~`0017`, 2026-07-29)

**"발신번호가 있어야 붙일 수 있다"가 틀렸다.** 보호자 앱이 이미 PWA라 채널은 이미 있었다.
문자·알림톡을 기다릴 이유가 없었고, 발신번호·사업자등록·건당요금이 전부 불필요하다.

- 대상 세 종류. 전부 **직원 전용 DEFINER** 로만 찾는다 — 구독 한 줄은 "그 기기로 알림을 보낼 수 있는 열쇠"라
  직원조차 테이블을 직접 못 읽는다.
  · 보호자 `push_targets_for_patient`(owner_id) · 1차병원 `push_targets_for_hospital`(referring_hospital_id)
  · 우리 직원 `push_targets_staff`
- **알림 본문에는 이름과 "왔다"까지만.** 잠금화면은 누구나 본다.
- 발송 실패가 리포트 저장을 되돌리지 않는다. 410/404 면 그 기기를 죽은 것으로 표시하고 다음부터 건너뛴다.
- ⚠️ VAPID **공개키를 바꾸면 기존 구독이 전부 무효**가 된다. `CONSENT_ENC_KEY` 처럼 따로 백업.

**남은 변수는 도달률.** iOS 는 홈 화면에 추가해야 푸시가 온다(안드로이드·데스크탑은 브라우저에서 바로).
즉 **"홈 화면에 추가" 전환율 = 알림 도달률**이고, 이 숫자를 보호자 사용률과 함께 봐야 한다.

## 입원 리포트 — 단순화 + 작성/발송 분리 (`0014`, `0017`)

  (사람마다 "조금 먹음"과 "잘 안 먹음"이 다르면 보호자는 악화로 읽는다).

- **작성자와 발송 판단자가 다르다** — 병동 입력은 간호사, 보호자에게 내보낼지는 수의사.

  회차 리포트는 수의사가 직접 쓰므로 이 단계가 없다(즉시 발송).
- DB 역할은 아직 `staff` 하나다. 간호사/수의사 구분이 필요해지면 `profile` 에 직종을 넣어야 한다.

## 진료 기록 형식 — 자유 노트가 기본 (2026-07-29 결정)

원장이 수의사들에게 물어본 결과: **SOAP 를 실제로는 잘 안 쓴다. 불편하다.**

- 시연 데이터도 **2/3 을 자유 노트로** 바꿨다. 데모가 한 형식만 보여주면 그게 곧 강요로 읽힌다.

## 보호자 앱 화면 정리 (2026-07-29 오후)

실제로 폰에서 눌러 보며 나온 것들. 대부분 **구조 문제**였지 디자인 문제가 아니었다.

  ⚠️ 탭에서 뺐으면 **라우트도 지우거나 리다이렉트**해야 한다. 목록 라우트만 남겨 뒀다가

  입원 화면과 중복됐다 → 회차에는 링크만. 어느 쪽이 최신인지 보호자가 판단하게 만들면 안 된다.
- **안 읽음은 세 가지가 한 세트다**: 탭 배지(개수) · 맨 위 "새로 온 리포트" 모아보기(위치) · 목록 항목 강조(맥락).
  개수만 있으면 27개를 뒤져야 한다. 그리고 **안 읽은 목록은 피드를 잘라 만들지 말 것** —
  50건 창 밖으로 밀린 항목 때문에 배지(3)와 목록(2)이 어긋났다(`unreadFeed` 로 직접 조회).
- **읽으면 배지가 즉시 줄어야 한다.** 배지를 든 레이아웃은 페이지보다 먼저 렌더되므로
  읽음 처리 후 `router.refresh()` 를 한 번 부른다(이번에 실제로 읽은 게 있을 때만).
- **병원 소식에는 우리 아이 얘기를 넣지 않는다.** 매일 보는 화면이 자기소개로 시작할 이유가 없다.

  서명 시각·IP·기기·본문 스냅샷은 남기고 있으나 법적 확인은 별개다.
- **고유식별정보 접근 로그** — 환자 기록 열람은 `access_log`에 남지만 **주민번호 복호화 이력은 아직 없다.**
  개인정보보호법상 접근기록 보관 대상이라 `log_access`에 `target='consent_rrn'` 을 붙이는 정도로 끝난다.
- **`/referral` 브라우저 확인 미완** — 원장 계정으로 화면을 눌러보진 않았다.
  보호자 리포트·미리보기·대시보드·시드는 실제 화면에서 확인했다 (전송 → 저장 → 보호자 앱 렌더까지).
