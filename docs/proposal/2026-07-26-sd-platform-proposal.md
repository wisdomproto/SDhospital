# SD동물의료센터 레퍼럴 플랫폼 사업 기획서

> **한 줄 요약** — 우리 아이가 오늘 무슨 진료를 받았는지 **매 방문마다 보호자에게 보내주는 앱**을 만듭니다.
> 입원하면 거기에 더해 **매일 경과가 쌓입니다.**
> 보호자는 안심하고, 다시 오고, 지인에게 말합니다. 의뢰한 1차 병원에도 같은 기록이 열립니다.
> 목표는 **한 번 온 환자를 평생 환자로 만드는 것**, 그리고 그 결과로서의 **SD동물의료센터 매출**.
>
> **이번에 만드는 것은 MVP — 보호자 앱 + 1차 병원 열람 화면, 4~5개월.**
> 1차 병원 EMR·PACS·AI는 **만들지 않습니다.** 보호자가 실제로 쓰는지 숫자로 확인한 뒤에 결정합니다.

- 작성일: 2026-07-26
- 대상: SD동물의료센터 (서울점 / 김포점) 원장님
- 문서 성격: 사업 방향 + 제품 구성 + 개발 로드맵 (금액은 별도 견적서)

## 1. 왜 지금, 왜 이 플랫폼인가

### 1.1 2차 병원 매출의 구조

2차(의뢰) 동물병원의 매출은 **"동네 병원이 못 하는 수술·검사"** 에서 나옵니다. 이 매출은 두 가지 특성이 있습니다.

| 특성 | 의미 |
|---|---|
| **빈도가 낮고 단가가 높다** | 보호자가 1년에 몇 번 오지 않지만, 한 건이 크다 |
| **거리 저항이 낮다** | 큰 수술은 동네에서 못 하므로, 믿을 만하면 지방에서도 서울로 온다 |
| **유입 경로가 1차 병원에 종속된다** | 보호자는 "우리 동네 원장님이 보내준 병원"으로 간다 |

즉 **2차 병원의 영업사원은 전국의 1차 병원 원장님**입니다.
그런데 대부분의 2차 병원은 이 관계를 **개인 친분·전화·카톡**으로 관리하고 있습니다.

### 1.2 지금 새는 곳

| 새는 지점 | 현재 | 결과 |
|---|---|---|
| 의뢰 접수 | 전화 + 소견서 종이/카톡 사진 | 누가 얼마나 보내는지 데이터가 없음 |
| 영상 전달 | CD, 이메일, 카톡 압축파일 | 화질 손실, 분실, 재촬영 |
| 진행 상황 공유 | 1차 원장이 직접 전화해서 물어봄 | 응대 인력 소모, 1차 병원 불안 |
| 환송 | 퇴원 후 구두 설명 | 1차 병원이 후속 관리를 못 함 → 다음 의뢰가 끊김 |
| 보호자 | 입원 중 하루 종일 궁금함 | 매일 전화, 불만, 재방문 안 함 |

**모든 항목이 "다음 레퍼가 올 확률"을 깎아먹습니다.**

### 1.3 우리가 팔 것

> 1차 병원에게는 **지금까지 아무도 준 적 없는 것 — 내가 보낸 환자의 2차 진료 기록**,
> 보호자에게는 **내 강아지가 지금 어떤지 아는 안심**,
> SD에게는 **레퍼 유통망과 평생 고객**.

#### 이것이 왜 신규 서비스인가

레퍼가 발생하면 환자는 **SD로 직접 와서 SD에 등록**합니다. 그 순간부터의 진료 기록 —
검사 결과, 영상, 판독문, 수술 기록, 입원 경과 — 은 **전부 SD 안에만 남습니다.**
의뢰한 1차 병원 원장님은 자기가 보낸 환자가 어떻게 됐는지 **전화로 묻는 것 말고는 알 방법이 없습니다.**

**그걸 그대로 돌려드리는 서비스는 지금 국내에 없습니다.**

#### 그리고 서로 겹치지 않습니다

| | 1차 병원 | SD (2차) |
|---|---|---|
| 위치 | 보호자 집 근처 | 멀다 |
| 비용 | 저렴 | 비싸다 |
| 진료 | 예방접종·일반진료·후속관리 **(대부분)** | 수술·정밀검사 **(가끔)** |

환자는 어차피 **평상시 진료를 1차에서 계속 받습니다.** SD가 데이터를 공유한다고 해서
1차 병원의 환자가 SD로 넘어가지 않습니다. 오히려 1차 병원은 **더 나은 후속 관리**를 할 수 있게 됩니다.

> **결론: 이건 제로섬이 아닙니다.**
> 1차 병원은 잃는 것 없이 못 보던 정보를 얻고, SD는 다음 레퍼를 얻습니다.
> 그래서 **1차 병원이 거절할 이유가 없습니다.** 이 사업의 근거는 여기에 있습니다.

## 2. 플랫폼 전체 구조

```
        ┌──────────────────────────────────────────────┐
        │        SD 플랫폼 (하나의 클라우드)             │
        └──────────────────────────────────────────────┘
                            │
   ┌────────────────┬───────┴────────┬──────────────────┐
   │                │                │                  │
[1차 병원]       [SD 2차]        [보호자 앱]        [AI 엔진]
 EMR + PACS      본원 EMR         모바일             판독 보조
 (무상/저가)      + PACS          리포트/챗          RAG 챗
   │                │                │                  │
   └──── 의뢰 ─────▶│                │                  │
   ◀─── 환송/회신 ──┘                │                  │
                    └─── 실시간 리포팅 ┘
```

### 2.1 데이터 공유 원칙 — **양방향 명시 동의**

데이터 공유가 이 플랫폼의 상품 그 자체이므로, **무엇이 언제 누구에게 보이는지**가
계약서와 화면 양쪽에서 명확해야 합니다. 아래는 그 규칙입니다.

| 규칙 | 구현 |
|---|---|
| 1차 → 2차 | 1차 병원이 **환자 단위로 의뢰 버튼을 누른 그 환자만** SD가 조회 가능 |
| 2차 → 1차 | SD가 **의뢰받은 그 환자에 한해** 진료·영상·입원 기록을 1차에 공개 |
| 기본값 | **비공개**. 공유는 항상 명시적 행위로만 발생 |
| 범위 | 의뢰 건 종료 후에도 해당 환자 이력은 열람 가능(후속 관리용), 그 외 환자는 영원히 불가 |
| 소유권 | 1차 병원이 입력한 데이터의 **소유권은 1차 병원**. 탈퇴 시 전량 내보내기 제공 |
| 감사 | 누가 언제 어떤 환자 기록을 열었는지 **접근 로그 전부 기록**, 양측이 조회 가능 |
| 환송 원칙 | 치료 종료 시 **1차 병원으로 환송**하는 것을 제품 기본 흐름으로 (레퍼럴 에티켓의 제품화) |

기술적으로는 애플리케이션 코드가 아니라 **데이터베이스 계층(RLS, Row Level Security)** 에서 강제합니다.
앱에 버그가 나도 권한 없는 환자 기록은 조회 자체가 불가능합니다. — *현재 SD EMR에 이미 적용되어 동작 중*

## 3. 제품 구성

**MVP는 두 개뿐입니다. 그중 하나에 힘을 몰아줍니다.**

| 우선순위 | 축 | 내용 | 단계 |
|---|---|---|---|
| **1위** | **C. 보호자 앱** *(3.3)* | 입원 리포팅 · **맞춤 질문·답변** · 전자 동의서 · 검진 리포트 | **★ MVP 주력** |
| 2위 | **A. 레퍼럴 브릿지** *(3.1)* | 1차 병원이 자기 의뢰 환자를 보는 화면 + 알림 | **▶ MVP 포함** |
| — | **B. 공유 레이어** *(3.2)* | 데이터를 담는 그릇 | ✅ **구축 완료** |
| 이후 | **D. 1차 병원 EMR + PACS** *(3.4)* | 신규 개척 영업 무기 | ⏸ 게이트 통과 후 |
| 이후 | **E. AI** *(3.5)* | 판독 보조 · 보호자 AI 챗(FAQ 커버율 보고 판단) | ⏸ 이후 |

> ### ★ 왜 보호자 앱에 힘을 몰아주는가
>
> **결국 만족해야 하는 사람은 보호자입니다.**
> 1차 병원 원장님은 환자를 **보내주는 사람**이지만, 다시 오고 지인에게 말하는 사람은 보호자입니다.
> 그리고 **1차 병원 원장님을 움직이는 것도 결국 보호자의 만족**입니다 —
> "거기 보냈더니 우리 보호자가 너무 좋아하더라"만큼 강한 영업이 없습니다.
>
> 반대로 직원용 EMR 쪽은 **깊이 만들 이유가 없습니다.**
> SD는 **기존에 쓰던 시스템을 계속 쓰실 것**이므로, 우리 화면은 그걸 대체하지 않습니다.
> 여기에 기능을 더 넣어봐야 아무도 쓰지 않습니다.
>
> **→ 직원 쪽은 최소한으로, 보호자 앱은 완성도를 끝까지.**

> ### 🚦 게이트 — 만족이 먼저, 확장은 그다음
>
> **1차 병원 EMR·PACS·AI는 만들지 않고 시작합니다.**
> 이 사업은 **"보호자가 만족하면 재방문·바이럴·레퍼가 늘어난다"** 는 하나의 가설 위에 서 있습니다.
> 맞으면 확장할 근거가 생기고, 틀리면 EMR을 만들어 봐야 결과는 같습니다.
> **검증 안 된 가설 위에 6개월치 개발을 얹지 않습니다.**

### 3.1 축 A — 레퍼럴 브릿지 ▶ **1차 목표**

**이것이 1차 목표의 전부입니다.** 새로 만드는 게 아니라 **이미 동작 중인 1차 병원 포털을 실전용으로 끌어올리는 일**입니다.

#### 지금 있는 것 → 무엇을 더하나

| | 현재 상태 | 비고 |
|---|---|---|
| 화면 | ✅ 의뢰 환자 목록 · 진료 회차 · 입원/바이털 조회 | Phase 0에서 완성 |
| **진행 상태** | ✅ **완료** — 진료중 / 입원중 / 퇴원 / 진료종료 / 환송완료 | 목록과 회차마다 배지로 표시 |
| **환송 소견서** | ✅ **완료** — 회차 화면에서 회신 작성 → 1차 병원 화면에 노출 | 원장님은 진료 원문·처방도 그대로 보십니다 |
| **레퍼 대시보드** | ✅ **완료** — 병원별 최근 90일 vs 직전 90일 · **의뢰 끊김** · **미환송** | 아래 참조 |
| 감사 | ✅ **완료** — 접근 로그(누가 언제 어떤 기록을 열었는지) | 외부 사용자는 기록을 남길 수만 있고 지울 수 없습니다 |
| **알림** | ✅ **완료** — 입원 / 퇴원 / 환송 소견 도착 시 원장님 기기로 푸시 | 아래 참조 |
| 계정 발급 | 초대 링크 있음 | 온보딩 간소화 (병원 등록 → 링크 발송 1분) |

> **💡 알림 — 문자가 아니라 앱 알림으로 해결했습니다.**
> 원장님도 보호자도 **매일 우리 사이트에 들어와서 확인할 리가 없습니다.** 밀어야 합니다.
>
> 처음에는 문자·알림톡을 생각했는데, **발신번호 등록·사업자 심사·건당 요금**이 붙습니다.
> 대신 이 서비스는 **앱(PWA)** 이라 **휴대폰 알림을 그대로 씁니다.**
> 등록 절차도, 심사도, 건당 요금도 없습니다. 이미 붙어 있고 동작합니다.
>
> ⚠️ 단 하나의 조건: **아이폰은 "홈 화면에 추가"를 해야 알림이 옵니다** (안드로이드·PC는 바로 됩니다).
> 그래서 **설치 안내가 곧 알림 설정**이고, 이 전환율이 곧 도달률입니다. 앱 안에서 계속 안내합니다.

#### 레퍼 대시보드 *(원장님 전용 — 게이트 판정 도구)* ✅ **동작 중**

`1차 병원` 화면에서 병원마다 바로 보입니다.

- **최근 90일 N건 (직전 90일 M건)** — 총건수보다 추세가 중요합니다
- **누적 건수 · 최근 의뢰일**
- 🔺 **의뢰 끊김** — 최근 90일 의뢰가 0인데 그 전에는 있던 병원
- 🔺 **미환송 N** — 진료는 끝났는데 아직 회신을 안 보낸 건수 (우리가 밀린 일)

이 화면 하나로 **"누구를 만나러 가야 하는지"** 가 명확해집니다.
아직 없는 것: 의뢰 → 실제 매출 전환 금액(청구 데이터 필요), 도입 전후 비교(기준선 확보 후).

#### 1차 목표에서 **하지 않는 것**

| 안 하는 것 | 이유 |
|---|---|
| 1차 병원용 EMR | 게이트 통과 후 (3.4) |
| 1차 병원용 PACS · DICOM 수신 | 상동. SD 영상은 기존 이미지 업로드로 공유 |
| AI 판독 | PACS와 한 묶음 → 이후 |
| 1차 EMR 내 원클릭 의뢰 | 1차에 우리 EMR이 없으므로 불가. **의뢰는 지금처럼 전화로** |

> **1차 병원은 아무것도 설치하지 않습니다.** 지금처럼 전화로 의뢰하고, 링크 하나 받아 결과를 봅니다.
> 바꿔야 할 습관이 없다는 것 — 이것이 1차 목표를 **몇 달 안에 끝낼 수 있는 이유**입니다.

### 3.2 축 B — 공유 레이어 *(이미 구축 완료)*

**SD가 기존에 쓰시는 시스템을 대체하지 않습니다.** 이건 EMR이 아니라
**보호자와 1차 병원에게 보여줄 것만 담는 그릇**입니다. 이미 만들어져 동작 중입니다.

| 기능 | 상태 |
|---|---|
| 환자·보호자·의뢰병원 관리 | ✅ 완료 |
| 진료 회차, 처방, 약품 마스터 | ✅ 완료 |
| 의료영상·사진/영상 업로드 | ✅ 완료 |
| 입원 관리 + 바이털 시계열 그래프 | ✅ 완료 |
| 초대 기반 외부 계정 발급 | ✅ 완료 |
| 1차 병원 원장용 읽기전용 포털 | ✅ 완료 |
| 보호자용 모바일 포털 | ✅ 완료 |

**즉, 이 사업은 0에서 시작하지 않습니다.** 그릇은 이미 있고, MVP는 여기에 **보호자 앱을 얹는 일**입니다.

#### 데이터 구조 — **모든 것의 기본은 진료(회차)**

```
  환자
   └─ 진료 회차 (visit)  ← 항상 생성됩니다
        ├─ 진단 · 처방 · 영상
        └─ 입원 (admission)  ← 그 회차에 입원이 필요하면 딸려 붙는 별도 기록
             └─ 바이털 · 일일 경과
```

**입원하러 온 환자도 진료 기록이 먼저 만들어집니다.**
입원은 "다른 종류의 방문"이 아니라, **그 진료 회차에 딸린 추가 기록**입니다.
그래서 어떤 환자든 리포팅의 기준점은 항상 **진료 회차 하나**이고,
입원한 경우 그 회차 아래로 일일 경과가 쌓입니다.

| | 진료 회차 | 입원 |
|---|---|---|
| 성격 | **기본 · 항상 존재** | 그 회차에 필요할 때만 |
| 단위 | 방문 1건 | 회차에 딸린 별도 기록 |
| 보호자에게 | **회차 리포트** (진단·처방·영상·다음 계획) | **일일 리포트** (사진·바이털·경과) |

> **⚠️ 여기서 MVP 설계가 한 번 바뀝니다.**
> 처음에는 "입원 일일 리포트"를 앱의 심장으로 잡았습니다.
> 하지만 **모든 환자에게 반드시 생기는 것은 진료 회차**이고, 입원은 거기에 딸리는 기록입니다.
> 입원에만 걸어두면 **입원하지 않은 진료에는 앱이 아무 말도 하지 못합니다.**
>
> **→ 기본은 회차 리포트, 입원 일일 리포트는 그 위에 얹는 심화입니다.**
> 입원한 환자는 **둘 다 받습니다** — 회차 리포트 한 장 + 입원 기간 동안 매일 경과.
>
> 대신 **입력 건수는 늘어납니다.** 그래서 회차 리포트는 **진료 종료 시 한 번**,
> 입원 리포트는 **입원 중 하루 한 번**으로 나누고, 둘 다 30초 원칙을 그대로 적용합니다.

*⚠️ 현재 DB는 입원이 환자에 직접 붙어 있어(`admission.patient_id`) 회차와 형제 관계입니다.
**MVP 착수 시 회차 하위로 옮기는 스키마 정정이 선행되어야 합니다.** (작업량은 크지 않습니다)*

#### 데이터 입력 — **당분간 수의사가 직접 입력합니다** *(결정됨)*

기존 시스템을 계속 쓰시므로, 보호자에게 보여줄 내용은 **의료진이 따로 입력**합니다.
기존 EMR과의 자동 연동은 국내 EMR이 데이터를 열어줄 가능성이 낮아 초기에는 고려하지 않습니다.

**번거로움을 감수하고 시작하는 것으로 결정되었습니다.** 다만 그 번거로움이 **몇 달 뒤에도 유지되도록**
제품이 받쳐줘야 합니다. 초기엔 의욕으로 입력되다가 **3개월쯤 지나면 조용히 빠지는 것**이
이런 시스템이 실패하는 가장 흔한 경로입니다.

**그래서 MVP에 다음을 넣습니다.**

| 장치 | 내용 |
|---|---|
| **입력 부담 최소화** | 모바일 화면 1개, **탭 5회 이내**. 사진 찍기 → 바이털 → 한 줄. 나머지는 자동 조립 |
| **재입력 없애기** | 어제 값 자동 표시 후 변경분만 수정. 자주 쓰는 문구는 버튼으로 |
| **미입력 알림** ★ | 리포트가 안 나간 **오늘 회차 + 입원 환자**를 화면 상단에 상시 표시 |
| **누락 리포트** | 주간 입력률을 원장님 대시보드에 표시 — 빠지기 시작하면 바로 보입니다 |
| 범위 한정 | **회차는 종료 시 한 번**, 입원은 하루 한 번, 검진은 결과 나올 때 한 번 |
| **형식 강요 안 함** ✅ | 진료 내용은 **그냥 자유 노트**입니다. SOAP 등 틀은 원하는 분만 메뉴에서 꺼내 씁니다 |
| **입원은 간호사 입력 → 수의사 확인** ✅ | 병동에서 준비를 마치면 **수의사 휴대폰으로 알림**, 확인 후 보호자에게 발송 |

> **여쭤보니 SOAP를 실제로는 잘 안 쓰신다고 해서, 형식을 기본값으로 두지 않았습니다.**
> 화면에 틀 버튼을 붙여 놓으면 그게 곧 "이렇게 쓰라"는 지시가 됩니다. 자유롭게 적으시고,
> 필요한 분만 메뉴에서 틀을 꺼내 쓰시면 됩니다.
>
> **입원 리포트도 하루 두 가지만 고르면 끝납니다** — 잘 먹었는지 · 잘 쌌는지. 특이사항은 있을 때만.
> 체온·심박 같은 수치는 기록에 남지만 **보호자에게는 나가지 않습니다**(숫자는 안심을 주지 못합니다).

> **보호자가 원하는 것은 진료 차트가 아니라 "우리 아이 지금 어때요"입니다.**
> 차트를 통째로 옮길 필요가 애초에 없습니다. 사진 두세 장과 한 줄이 차트 열 장보다 낫습니다.
> **입력량을 줄이는 것이 곧 데이터가 계속 쌓이게 하는 방법입니다.**

#### ★ 입력 화면 UI/UX — **보호자 앱과 동급으로 공들입니다**

수기 입력을 전제로 하는 이상, **입력 화면의 사용성이 이 사업의 생명줄**입니다.
보통 이런 화면은 "직원용이니까" 하고 대충 만들지만, **여기서는 반대로 갑니다.**
보호자 앱과 **같은 수준의 디자인·공수**를 배정합니다.

**목표 동작 — 오늘 할 일이 한 화면에, 한 건당 30초로 끝납니다.**

```
  오늘 할 일 (폰 / 태블릿)
  ┌──────────────────────────────┐
  │  오늘 진료 12건 · 입원 5마리   │
  │  ⚠️ 아직 4건 미입력            │ ← 빨간 배지, 안 하면 계속 보임
  ├──────────────────────────────┤
  │  🔴 초코   진료 리포트  미입력→│ ← 모든 진료에 뜸
  │  🔴 보리   진료 리포트  미입력→│    (입원 여부와 무관)
  │  🔴 보리   입원 3일차   미입력→│ ← 입원 중이면 매일 한 줄 더
  │  ✅ 콩이   입원 5일차   09:12  │
  │  ✅ 두부   진료 리포트  14:20  │
  └──────────────────────────────┘
   ※ 보리처럼 입원 중인 환자는 진료 리포트와 입원 리포트가
     각각 뜹니다. 회차는 한 번, 입원은 매일.
              ↓ 탭
  ┌──────────────────────────────┐
  │  📷  [카메라 바로 열림]        │ ← 찍으면 자동 첨부, 2~3장
  ├──────────────────────────────┤
  │  ▸ 회차 리포트면              │
  │    [진단] [처방] ← 자동 불러옴 │
  │  ▸ 입원 리포트면              │
  │    체온 38.4 심박 96 호흡 24  │ ← 어제 값 프리필,
  │    [숫자패드 - 큰 버튼]        │    바뀐 것만 수정
  ├──────────────────────────────┤
  │  한 줄 코멘트                 │
  │  [🎤 음성]                    │ ← 말하면 받아쓰기
  │  [경과 양호] [식욕 회복]      │ ← 자주 쓰는 문구 버튼
  │  [드레싱 완료] [재방문 안내]   │
  ├──────────────────────────────┤
  │       [ 보 내 기 ]            │ ← 누르는 즉시 보호자에게 푸시
  └──────────────────────────────┘
```

**화면은 하나입니다.** 회차냐 입원이냐에 따라 가운데 입력란만 바뀝니다.
의료진이 "어디에 들어가서 뭘 눌러야 하지"를 고민하는 순간 입력은 끊깁니다.

**설계 원칙**

| 원칙 | 이유 |
|---|---|
| **탭 5회 이내, 화면 1개** | 병동에서 오래 붙잡고 있을 수 없습니다 |
| **어제 값 자동 채움** | 대부분 안 바뀝니다. 바뀐 것만 고치게 |
| **카메라 즉시 실행** | 사진이 리포트의 8할. 앨범 고르기 단계를 없앰 |
| **음성 입력 + 자주 쓰는 문구 버튼** | 타이핑이 가장 큰 저항. 말하거나 누르게 |
| **큰 터치 영역** | 장갑 낀 손, 급한 상황 |
| **오프라인 저장 후 자동 동기화** | 병동 전파가 약해도 입력이 날아가지 않게 |
| **미입력이 계속 보이게** | 잊는 게 아니라 밀리는 겁니다. 눈에 띄면 하게 됩니다 |
| **저장 = 발송** | 확인 단계 없음. 한 번 더 누르게 하면 안 합니다 |

> **검수 기준**: 실제 현장에서 **하루치(회차 12건 + 입원 5마리)를 10분 안에** 처리할 수 있어야 합니다.
> 이걸 못 넘기면 기능을 더 빼고 다시 만듭니다.

### 3.3 축 C — 보호자 앱 ★ **MVP 주력**

**이 앱이 제품입니다.** 나머지는 이 앱을 받쳐주는 부속입니다.

> **여기는 "돌아가면 됨" 수준으로 만들지 않습니다.**
> 보호자는 카카오톡·인스타그램·쿠팡을 매일 쓰는 사람입니다. 그 눈높이와 비교당합니다.
> 병원 앱이라고 촌스러우면 **한 번 열고 안 엽니다.** 그러면 이 사업의 가설 자체를 검증할 수 없습니다.
>
> **MVP의 "M"은 기능 수를 줄인다는 뜻이지, 완성도를 낮춘다는 뜻이 아닙니다.**
> 기능은 아래 6개로 좁히되, **각각은 끝까지 다듬습니다** — 로딩 속도, 애니메이션, 사진 화질,
> 푸시 문구, 빈 화면 처리, 글자 크기(보호자 연령대가 넓습니다)까지.

#### C-0. 앱 구성 ✅

> 아래 네 개가 앱의 전부입니다. **입원은 따로 두지 않았습니다** — 입원은 진료에 딸린 기록이라
> 해당 진료 아래에 붙습니다. 보호자가 "그게 어느 진료였더라"를 되짚지 않아도 됩니다.

| 탭 | 내용 |
|---|---|
| **병원 소식** | 공지·이벤트·쿠폰, 서명이 필요한 동의서, 최근 리포트 |
| **진료 기록** | 회차 목록(입원은 그 아래) · 새로 온 리포트 모아보기 |
| **AI 채팅** | 준비 중 (C-2) |
| **내 정보** | 반려동물 사진·기본 정보, 알림 켜기 |

- **새 리포트 표시**는 세 곳에서 같이 알려드립니다 — 탭 배지(개수), 맨 위 모아보기(위치), 목록 강조(맥락).
  숫자만 띄우면 27개 목록에서 찾아야 합니다
- **앱을 열면 마지막에 보던 아이로 바로 들어갑니다.** 매번 고르게 하지 않습니다
- **반려동물이 여러 마리**면 위쪽 이름을 눌러 바꿉니다. 보던 화면은 그대로 유지됩니다
- **프로필 사진**은 보호자가 직접 올립니다. 목록에서 이모지 대신 우리 아이 얼굴이 보입니다

#### C-1. 진료 리포팅 — *가장 중요한 기능*

리포트는 **두 종류**이고, 데이터 구조를 그대로 따릅니다 (3.2).

**① 회차 리포트 — 기본. 모든 환자가 매 방문마다 받습니다.**

✅ **완료 — 실제 화면입니다.**

```
  ┌──────────────────────────────────────┐
  │  🐕 보행 시 균형 불균형 진료 리포트     │
  │     개 · 푸들 · 15세 1개월 · 6.36kg    │
  ├──────────────────────────────────────┤
  │  📈 지난 방문 대비 별이의 변화          │
  │   · 지난 5월 6일 방문에는 각막궤양으로  │
  │     내원하셨어요                       │
  │   · 이번에는 보행 시 균형 불균형으로     │
  │     내원하셨어요                       │
  │   · 체중은 6.1kg → 6.36kg (+0.26kg)   │
  ├──────────────────────────────────────┤
  │  🐾 별이의 상태예요                    │
  │   · 보행 시 균형을 잡지 못하는 증상     │
  │   · 눈이 왔다 갔다 하는 증상           │
  ├──────────────────────────────────────┤
  │  📋 추가 안내 사항이에요                │
  │   당분간 계단은 피해주세요              │
  └──────────────────────────────────────┘
```

> **⚠️ 처방 상세(약품·용량)와 진료 원문은 넣지 않습니다** — 원장님 지시대로 분쟁 소지를 없앴습니다.
> 보호자에게는 **어떤 문제로 왔고 · 어떤 검사를 했고 · 어떤 치료를 받았는지**만 나갑니다.
>
> **선생님이 입력하시는 건 세 가지뿐입니다** — 주 증상 한 줄 · 코멘트 · (선택) 추가 안내.
> 제목·프로필·나이·**지난 방문 대비 변화**는 시스템이 계산합니다.
> 다만 **진료 원문을 요약해서 내보내지는 않습니다.** 우리가 줄인 문장의 책임은 병원이 지게 됩니다.

**보내기 전 미리보기** ✅ — 보호자가 볼 화면을 그대로 띄우고 [수정] / [전송]을 고릅니다.
저장된 값이 아니라 **지금 입력 중인 값**으로 만들기 때문에, 미리보기가 곧 실제 발송물입니다.

**② 입원 일일 리포트 — 입원한 회차에만, 매일 한 번.**

```
  ┌─────────────────────────────┐
  │  🐕 초코 · 입원 3일차         │
  ├─────────────────────────────┤
  │  오늘 오전 사진 3장           │
  │  식사  밥을 잘 먹었어요        │
  │  배변  대소변 모두 정상이었어요 │
  │  담당의 코멘트:               │
  │  "식욕 돌아왔습니다. 내일      │
  │   드레싱 후 경과 봅니다."      │
  ├─────────────────────────────┤
  │  [입원 경과 전체 보기]        │
  └─────────────────────────────┘
```

- **회차 리포트가 앱을 살아 있게 합니다.** 진료 회차는 어떤 환자에게든 반드시 생기므로,
  앱이 말을 걸 기회가 **모든 방문마다** 생깁니다.
- **입원한 환자는 둘 다 받습니다** — 입원 시 만들어진 회차 리포트 한 장,
  그리고 입원 기간 동안 **매일 쌓이는 일일 리포트**. 불안이 가장 큰 구간이라 밀도를 높입니다.
- 퇴원·치료 종료 시 **종합 리포트 자동 생성**: 담당의 코멘트, 진행한 검사, 사진·영상,
  입원 기간·바이털 범위, 날짜별 경과 (PDF 저장·공유)
- 담당 수의사는 **선택지와 한 줄 코멘트만** — 나머지는 시스템이 자동 조립
  *(현장 부담이 크면 아무도 안 씁니다. 건당 30초가 설계 기준입니다.)*

> ### ⚠️ 보호자에게 무엇을 보여줄 것인가
>
> **상세 처방 데이터(약품·용량·용법·기간)는 보호자에게 내보내지 않습니다.** 분쟁의 소지가 됩니다.
> 진료 기록 원문도 마찬가지입니다 — 의료진 축약어와 감별진단이 섞여 있어
> 보호자가 검색해보고 불안해하거나 확정 진단으로 오해합니다.
>
> 보호자에게는 **"어떤 문제로 왔고 · 어떤 검사를 했고 · 어떤 치료를 받았는지"** 수준으로 나갑니다:
> 담당의 코멘트 + 진행한 검사 요약 + 사진·영상 + (입원 시) 날짜별 경과.
>
> **1차 병원 원장님 화면은 다릅니다** — 처방·진료 원문 전부 보입니다. 의료진이니까요.

#### C-2. 맞춤 질문·답변 ▶ **MVP 포함**

리포트 아래에 **그 아이 상황에 맞는 질문**이 버튼으로 뜨고, 누르면 **병원이 미리 써 둔 답변**이 나옵니다.

```
  🐕 초코 · 슬개골 수술 리포트
  담당의 코멘트: "수술 잘 끝났습니다…"
  ─────────────────────────────
  이런 게 궁금하실 것 같아요
   › 언제부터 산책시켜도 되나요?
   › 계단 올라가도 되나요?
   › 실밥은 언제 뽑나요?
   › 약 먹고 토하면 어떡하죠?
```

**AI가 아니라 병원이 쓴 문장이 나갑니다.** 이게 이 방식의 핵심 장점입니다 —
AI가 잘못 말하면 그 책임이 병원에 돌아오지만, 수의사가 검수한 답변만 나가면 그 위험이 없습니다.
API 사용료도 들지 않습니다.

**조합이 아니라 조건으로 만듭니다.** 품종 200 × 나이대 4 × 질병 100을 다 쓰면 8만 개가 되어 관리가 불가능합니다.
답변 하나에 **"언제 보여줄지" 조건**을 붙여, 하나의 답변이 여러 상황에 재사용되게 합니다.

| 조건 축 | 예 |
|---|---|
| 진단 · 처치 | 슬개골탈구교정 → "산책은 2주 후부터…" |
| **품종군** | 소형견 / 대형견 / 단두종 / 고양이 |
| 나이대 | 1세 미만 / 성견 / 7세 이상 |
| 상황 | 수술 전 / 입원 중 / 퇴원 직후 / 검진 결과 |
| 없음 | 면회 시간, 주차 안내 등 전체 공지 |

> **품종은 개별이 아니라 품종군으로 묶습니다.** 말티즈·포메라니안·치와와를 각각 쓰지 않고 "소형견"으로 묶습니다.
> 그래서 **새 품종이 들어와도 그룹에 넣기만 하면 기존 답변 수십 개가 자동으로 따라옵니다.**

**재료는 SD가 이미 가지고 있습니다.** 원장님께서 보유하신 **10년치 상담 대화 기록**이
질문 목록의 근거가 됩니다. 저희가 상상해서 만든 질문 30개와, 10년간 실제로 보호자가 물어본 것에서
뽑은 질문은 전혀 다른 물건입니다.

**직원이 직접 고칠 수 있어야 합니다.** 질문·답변·조건을 관리하는 화면을 함께 만듭니다.
문구 하나 고치는 데 개발사를 불러야 하면, 그 기능은 그 순간부터 갱신이 멈춥니다.

**한계도 분명합니다.** *"우리 초코 신장 수치가 왜 올랐나요?"* 같은 개별 질문은 답할 수 없습니다.
그건 결국 전화로 옵니다. 전화 문의 감소 효과는 AI보다 작습니다.

**대신 데이터가 쌓입니다** — 어떤 질문이 많이 눌리는지, *"찾는 답이 없어요"* 를 누른 보호자가 무엇을 물었는지.
이 숫자가 **AI를 도입할지 말지를 감이 아니라 근거로** 판단하게 해줍니다 (C-2b).

#### C-2b. AI 채팅 (진료 기록 기반) ⏸ *(MVP 제외 — 이후)*

C-2의 커버율이 낮게 나올 때 검토합니다.

- 우리 아이의 **실제 진료 기록·판독문·처방을 근거로** 답변
- 근거가 된 기록을 **출처로 함께 표시** (환각 방지)
- **진단·처방을 하지 않습니다.** 위험 신호 감지 시 즉시 내원/응급 안내로 전환 (4.2 참조)
- 야간·주말 전화 문의를 흡수 → 응대 인력 절감
- 기술적으로는 **검색(RAG)이 필요 없습니다.** 대상이 그 아이 한 마리이고 기록 전체가 몇 KB라
  통째로 넣으면 됩니다. 벡터DB는 C-3(치료 사례 검색)에서 처음 필요해집니다.

#### C-3. 치료 사례 제시 ✅ **완료**

> **원장님이 새로 쓰실 글은 없습니다.** sdamc.co.kr 에 이미 수백 건이 올라와 있고,
> 보호자가 그걸 못 볼 뿐이었습니다. 링크와 태그만 등록하면 됩니다.

- 리포트 아래에 **"같은 문제로 치료받은 아이들"** — 우리 아이와 같은 문제, 같은 종의 사례만
- 새 사례를 만들지 않고 **병원 블로그 글을 링크**합니다. 글은 병원 것이고, 고치면 그쪽에서 고쳐집니다
- 보호자 사례를 가져다 쓰지 않으므로 **동의·비식별 문제가 없습니다**
- **맞는 사례가 없으면 아무것도 안 붙입니다.** 상관없는 사례가 붙으면 보호자는 그걸 광고로 읽고,
  그 순간 리포트 전체의 신뢰가 깎입니다
- 사례 선택은 **AI가 아니라 태그**입니다. 틀리면 그 책임은 병원이 집니다

#### C-4. 진료별 전자 동의서 ▶ **MVP 포함**

SD에서 쓰시는 종이 양식 **5종을 그대로** 옮겼습니다 — 입원 / 수술·마취·검사 / 투석(CRRT) / 재활 / 퇴원 요청.

> **6종이 아니라 5종인 이유** — 슬개골탈구와 장생검은 **같은 "수술·마취·검사 동의서"** 입니다.
> ASA 표도, 마취 위험 4개 항목도 동일하고 **진단·처치·시술 설명만** 다릅니다.
> 그래서 하나의 양식으로 묶었고, **새로운 수술이 생겨도 설명 문구만 넣으면 됩니다.**

**흐름**: 회차 화면에서 발행 → 보호자 앱에 "서명이 필요합니다" → 본문 확인 →
선택지 체크(CPR/DNR, 사진 게시 여부) → **손으로 서명** → 완료.
**병원 태블릿으로 그 자리에서 받는 것도 같은 화면**입니다. 앱을 안 깔았거나 내원 중인 보호자용입니다.

**증빙에서 중요한 건 서명 그림이 아니라 본문입니다.** 분쟁이 생기면 *"그때 무슨 문구에 동의했느냐"* 가
쟁점이 됩니다. 그래서 서명하는 순간 **그 시점의 본문 전문을 통째로 보관**합니다.
나중에 양식을 고쳐도 과거 서명은 그때 읽은 문장 그대로 남습니다. 서명 시각·IP·기기 정보도 함께 기록됩니다.

**주민등록번호는 암호화되어 저장됩니다.** 고유식별정보라 법적으로 암호화가 의무이고,
화면에는 항상 `900101-1******` 로 가려 보여줍니다.

**현장 효과**: 대기실 종이 설명 시간 단축, 분실 없는 보관, 분쟁 시 증빙.

#### C-5. 건강검진 데이터 리포팅

- 검진 결과를 수치표가 아니라 **그래프와 한글 설명**으로
- 연도별 추이 (신장 수치, 간 수치, 체중, 심장 크기…)
- "작년 대비 신장 수치가 올라가고 있습니다 → 6개월 뒤 재검 권장" → **재검 예약 버튼**
- **효과: 검진 → 재검 → 조기 발견 → 치료.** 검진 자체가 리텐션 엔진이 됩니다

#### C-6. 병원 소식·이벤트 ✅ **완료**

**보호자 앱 첫 화면입니다.** 리포트는 진료가 있어야 생기지만 소식은 언제든 낼 수 있고,
**진료가 없는 달에도 앱을 열 이유**를 만드는 건 이쪽입니다.

- 직원 화면에서 제목·내용·기간만 넣으면 등록됩니다 (`/notices`)
- **기간이 지나면 자동으로 사라집니다.** 내리는 걸 사람이 기억해야 하는 구조는 반드시 실패하고,
  지난 이벤트가 첫 화면에 걸려 있으면 그게 신뢰를 깎습니다
- **할인 쿠폰** — 쿠폰 문구를 적으면 쿠폰 카드로 나갑니다.
  코드도, 사용 처리도, 개인별 발급도 없습니다. **보호자가 앱 화면을 보여주면 접수에서 눈으로 확인**합니다.
  발급·사용 관리를 만들면 접수 데스크에 새 일이 생기고, 그러면 안 쓰게 됩니다
- 아직 안 한 것: 나이·품종·병력 기반 **개인화**, 1차 병원 공동 캠페인

### 3.4 축 D — 1차 병원용 EMR + PACS ⏸ *(게이트 통과 후)*

> **지금 개발하지 않습니다.** 아래는 게이트를 통과했을 때의 계획이며,
> "그다음에 뭘 할 건지"를 판단하시는 근거로만 읽어 주십시오.

#### ⚑ 1차 병원은 두 세그먼트로 완전히 다릅니다

| | **세그먼트 A — 이미 아는 병원** | **세그먼트 B — 모르는 병원** |
|---|---|---|
| 현황 | 이미 SD에 의뢰하고 있음 | **이미 친한 2차 병원이 따로 있음** |
| 규모 | 수십 곳 | **수천 곳 (성장 여력의 전부)** |
| 문제 | 관계 유지 | **찾아갈 명분이 없음** |
| 먹히는 것 | **뷰어 계정** ← *1차 목표가 노리는 곳* | 뷰어 계정은 안 먹힘 (**레퍼를 안 하니 볼 기록이 없음**) |
| 필요한 것 | — | **공짜 EMR + PACS + AI 판독** |

> **여기가 이 축의 존재 이유입니다.**
> 세그먼트 B의 원장님에게 "저희한테 의뢰해 주세요"는 통하지 않습니다. 이미 믿는 2차 병원이 있으니까요.
> 하지만 **"영상 클라우드 백업이랑 AI 판독, 공짜로 써보시겠습니까"** 는 만나줍니다.
> **파는 게 아니라 주는 거라 문이 열립니다.**
>
> 깔고 나면 그 원장님은 **매일 우리 화면을 봅니다.** 그리고 그 화면 안에 의뢰 버튼이 있습니다.
> 기존 2차 병원에 보내려면 전화하고 CD 굽고 소견서 써야 하는데, SD로 보내는 건 클릭 한 번입니다.
> **관계로는 못 이기지만, 마찰로는 이길 수 있습니다.**

#### 구성

- **PACS** *(창끝)*: DICOM 수신, 웹 뷰어(창 조절·확대·측정·주석), 클라우드 백업, AI 판독
- **EMR** *(클로징 옵션)*: 접수·수납·예약·차트·처방 + **EMR 내 원클릭 의뢰**
- 기존 EMR 데이터 마이그레이션 (전환 병원 확정 후, 그 병원 EMR에 맞춰서만)

> **⚠️ 냉정한 현실 진단 — 기능이 아니라 "갈아타기"가 장벽입니다**
> 동물병원 EMR의 기능 자체는 접수·수납·예약·차트 정도로, 기술적으로 어려운 영역이 아닙니다.
> *(사람 병원과 달리 의료보험 청구가 없고, 펫보험은 사보험이라 표준이 없어 청구 연동은 고려 대상이 아닙니다.)*
>
> 진짜 장벽은 **이미 깔려 있다는 사실**입니다. 인투씨엔에스(인투벳) 2,000여 곳, 이프렌즈 1,800여 곳.
> **수년치 차트가 그 안에 쌓여 있고, 직원들 손에 익어 있습니다.**
> 데이터 이전 + 직원 재교육 + 전환 중 진료 차질 — 이 비용이 "무료"보다 큽니다.
>
> **→ 그래서 세 단계로 나누고, 세그먼트별로 다른 단계를 겁니다.**
>
> | 단계 | 1차 병원이 하는 일 | 마찰 | 주 대상 | 시점 |
> |---|---|---|---|---|
> | **① 뷰어 계정** | 아무것도 설치 안 함. 링크 받아 로그인 | **거의 0** | 세그먼트 A | **▶ 1차 목표** |
> | **② PACS 도입** | 영상 장비 전송 설정만. 기존 EMR 그대로 사용 | 낮음 | **세그먼트 B (창끝)** | 게이트 후 |
> | **③ EMR 전환** | 차트 이전 + 직원 교육 | 높음 | 전환 의사 있는 곳만 | 게이트 후 |

> **⚠️ ③으로 갈 때의 최대 위험 — 세그먼트 A는 SD의 현재 매출원입니다.**
> 파트너 병원에 EMR을 깔았다가 **접수·수납이 멈추면 잃는 것은 소프트웨어 평판이 아니라 레퍼 관계 그 자체**입니다.
> 첫 전환 병원에서는 **기존 EMR을 끄지 않고 병행 운영**하고, 접수·수납은 맨 마지막에 전환하며,
> 전환일에는 **개발자가 현장에 상주**합니다.

### 3.5 축 E — AI ⏸ *(이후)*

**의료영상 AI 판독**
- 흉부/근골격 X-ray 이상 소견 탐지 + 위치 표시, 판독 소견 초안 생성
- **최종 진단과 책임은 항상 수의사에게 있음**을 화면과 출력물에 명시

**보호자 RAG 챗봇** — 3.3 C-2 · C-3 참조

> **⚠️ AI 판독은 자체 개발하지 않습니다.**
> 수의영상 AI는 데이터 수집·라벨링·임상 검증에 수년이 걸립니다. SK텔레콤 '엑스칼리버'가
> 5개 국립대 수의대와 협약을 맺고 질환 탐지 민감도 84~97% 수준을 확보하기까지 걸린 시간이 그 증거입니다.
> **1단계: 기존 상용 솔루션 연동/제휴** → **2단계: 축적된 CT·MRI 데이터로 2차 병원 특화 모델 자체 개발**.
> SD의 진짜 자산은 알고리즘이 아니라 **모이는 영상 데이터**입니다.

## 4. 리스크와 법적 검토

정직하게 말씀드립니다. 다음 항목들은 **개발 착수 전에 확인·정리되어야 합니다.**

### 4.1 사업 리스크

| 리스크 | 크기 | 대응 |
|---|---|---|
| **1차 병원이 EMR을 안 갈아탄다** | 높음 | **애초에 갈아타라고 하지 않습니다.** 뷰어 계정 → PACS → EMR 3단계 (3.1). ①은 설치가 없어 마찰 0 |
| **1차 병원이 "환자 뺏긴다" 우려** | **낮음** | 진료권이 겹치지 않음 (1.3). 그래도 환송을 제품 기본 흐름으로, 보호자 앱에 **의뢰 병원명 노출** |
| **1차 병원이 데이터 유출을 우려** | 낮음 | 데이터가 흐르는 방향이 주로 **SD → 1차**(받는 쪽). 접근 로그·소유권 조항으로 마무리 (2.1) |
| **1차 병원이 계정만 받고 레퍼는 안 늘린다** | **중간** | 실질 위험. 레퍼 대시보드로 병원별 추이를 보고 관리 (3.5). Phase 1 종료 지표로 검증 |
| **세그먼트 B가 기존 2차 병원과의 관계를 안 깬다** | **높음** | 관계로는 못 이깁니다. **마찰**로 이깁니다 — 우리 화면 안의 원클릭 의뢰 vs 전화+CD+소견서. 시간이 걸리는 싸움임을 전제 |
| **확정 고객 없이 EMR 선개발** | 중간 | **파일럿 병원 1곳 사전 합의를 Phase 3 착수 조건**으로 못 박음. 합의 안 되면 Phase 4를 먼저 진행 |
| **파일럿 병원의 진료가 멈춤 → 레퍼 관계까지 잃음** | **높음** ★ | 이 사업 최대 리스크. 기존 EMR 병행 유지, 접수·수납은 마지막 전환, 전환일 개발자 현장 상주 (3.1) |
| **현장 입력이 몇 달 뒤 조용히 끊김** | **높음** ★ | **이 사업 최대 리스크.** 수기 입력이 전제이므로 입력 화면에 보호자 앱과 동급 공수 배정 + 미입력 배지 + 주간 입력률 지표 (3.2). 8마리 5분을 검수 기준으로 |
| **기존 EMR 업체의 대응** | 중간 | 우리의 해자는 EMR이 아니라 **2차 병원 네트워크 + 보호자 관계**. EMR만으로는 못 이김 |
| **AI 판독 자체 개발 리스크** | 높음 | 1단계 제휴, 2단계 자체 개발 (3.3) |

### 4.2 법적 · 규제 검토 (착수 전 자문 필요)

| 항목 | 쟁점 | 방향 |
|---|---|---|
| **진료기록 보존** | 수의사법상 진료부 기록·보존 의무 및 보존 기간 | 법정 요건 확인 후 보존 정책 확정 (삭제 방지·백업 포함) |
| **개인정보** | 보호자 성명·연락처는 개인정보보호법 대상 (동물 정보는 보호자와 결합 시 개인정보) | 개인정보 처리방침, 수집·이용 동의, 국내 리전 저장, 암호화 |
| **보호자 질문 응대** | 수의사 아닌 주체의 **진단·처방으로 오인될 소지** | **MVP는 병원이 직접 쓴 답변만 나가므로 이 리스크가 사실상 없음**(C-2). AI 도입 시에만: "진단·처방이 아닌 안내" 명시, 위험 키워드 감지 시 내원 안내 전환, 로그 보관 |
| **비대면 진료** | 수의사법상 원격진료 허용 범위 | 앱은 **기록 열람·설명**에 한정. 진료 행위로 해석될 기능은 넣지 않음 |
| **전자 동의서 효력** | 전자서명의 법적 효력, 본인확인 수준 | 전자서명법 요건 검토. 서명 시각·기기·본인확인 기록 보관 |
| **병원 광고** | 표시광고법 (과장·허위 표시 금지) | 치료 사례는 실제 기록 기반 + 보호자 동의. "100% 완치" 류 표현 금지 |
| **치료 사례 활용** | 타인 반려동물 진료정보 이용 | 보호자 별도 동의 + 비식별 처리 (이름·병원·날짜 마스킹) |

> 이 표의 항목들은 **개발 범위가 아니라 계약 이전에 정리해야 할 사항**입니다.
> 특히 AI 챗봇과 전자 동의서는 수의사법·전자서명법 자문을 권합니다.

## ★ MVP — **보호자 앱** · **3~4개월**
> *목표: 입원 보호자가 매일 열어 보고, 퇴원 후에도 지우지 않는 앱*

**개발 리소스의 70%가 여기에 들어갑니다.**

| # | 항목 | 비고 |
|---|---|---|
| M-1 | **회차 리포트** + 푸시 — 진단·처방·영상·한 줄 | **★ 기본. 모든 환자** |
| M-1b | **입원 일일 리포트** + 푸시 — 사진·바이털·한 줄 | 입원한 회차에만 |
| M-0 | **스키마 정정** — 입원을 회차 하위로 (`admission.visit_id`) | 착수 시 선행. 작업량 작음 |
| M-2 | **입력 화면** ★ — 오늘 할 일 한 화면(회차+입원) · 카메라 즉시 실행 · 프리필 · 음성/버튼 코멘트 · 오프라인 저장 · 미입력 배지 | **보호자 앱과 동급 공수.** 3.2 참조 |
| M-3 | **퇴원 종합 리포트** 자동 생성 (PDF 저장·공유) | 자랑하게 만드는 물건 |
| M-4 | 건강검진 리포트 — 추이 그래프 + 한글 해설 + 재검 안내 | 리텐션 엔진 |
| M-5 | **전자 동의서** (서명·보관·PDF) | 현장 시간 절감 + 분쟁 대비 |
| M-6 | **병원 소식·이벤트 + 할인 쿠폰** | ✅ 완료 · 개인화는 이후 |
| M-8 | **맞춤 질문·답변** — 조건 매칭 + 직원용 관리 화면 | ⬜ **재료 대기**: 10년치 상담 기록 |
| M-9 | **치료 사례** — 병원 블로그 글을 같은 문제 리포트에 연결 | ✅ 완료 |
| M-7 | **완성도 — 보호자 앱 + 입력 화면 양쪽** · 디자인·속도·사진 화질·푸시 문구·큰 글자 모드 | **별도 항목으로 잡습니다** |

> **M-7을 별도 항목으로 잡은 이유**
> 완성도는 "남는 시간에 다듬는 것"으로 두면 **반드시 안 됩니다.**
> 일정과 공수를 따로 배정해야 실제로 다듬어집니다.
> **보호자 앱은 카톡·인스타와 비교당하고, 입력 화면은 매일 여덟 번 열립니다.** 둘 다 대충 만들 수 없습니다.

*출시는 웹앱(PWA)으로 먼저 — 설치 없이 링크로 열립니다. 스토어 출시는 반응 확인 후.*

## 🚦 **게이트 — 여기서 멈추고 숫자를 봅니다**

MVP 출시 후 **6개월 운영.** 그동안 개발은 **버그 수정과 완성도 다듬기만**, 새 기능은 만들지 않습니다.

| 판정 기준 | 통과선 |
|---|---|
| **회차 리포트 열람률** (진료 환자 기준) ★ | **80% 이상** |
| 마지막 진료 30일 후 앱 유지율 | 50% 이상 |
| 입원 관련 전화 문의 | 절반 감소 |
| 재방문율 (12개월 내) | 40% 이상 |
| 세그먼트 A 병원의 월 의뢰 건수 (도입 전 대비) | +30% 이상 |

- **통과** → 1차 병원 EMR·PACS로 확장. 모르는 병원 개척에 투자할 근거가 생깁니다.
- **미달** → **확장하지 않습니다.** 보호자가 안 쓰는 앱이면 EMR을 깔아도 결과는 같습니다.
  **여기서 멈추는 것이 돈을 버는 겁니다.**

## 6. 수익 구조

### 6.1 SD동물의료센터의 수익

| 경로 | 설명 |
|---|---|
| **레퍼 증가** *(주 수익)* | 1차 병원 100곳 × 월 1건 = 월 100건 신규 의뢰. 이것이 이 사업의 전부입니다 |
| **재방문·검진 리텐션** | 보호자 앱 → 검진 리포트 → 재검 → 조기 발견 → 치료 |
| **바이럴** | 만족한 보호자의 지인 추천 (입원 리포트는 캡처해서 자랑하게 됩니다) |
| **AI 판독 수수료** | 1차 병원 판독 건당 과금 (선택) |
| **데이터 자산** | 축적된 영상·진료 데이터 → 자체 AI 모델 → 장기적으로 별도 사업화 가능 |

### 6.2 1차 병원 과금 (확산이 목적이므로 최소화)

| 항목 | 정책 |
|---|---|
| 뷰어 계정 | **무료** (세그먼트 A 관계 유지) |
| PACS + 의뢰 브릿지 | **무료** (스토리지 원가만 발생 — **판매 상품이 아니라 세그먼트 B의 문을 여는 영업비**로 간주) |
| 대용량 스토리지 초과분 | 원가 수준 종량 |
| AI 판독 | 건당 과금 또는 월 정액 |
| 풀 EMR (Phase 3) | 시장가 이하 저가 정액 |

### 6.3 개발사(당사) 과금 구조 (제안)

| 방식 | 내용 |
|---|---|
| **구축비** | Phase 단위 계약. 각 Phase 착수/완료 분할 지급 |
| **유지보수** | 월 정액 (서버 운영·장애 대응·소규모 개선) |
| **인프라 비용** | 클라우드 사용료 실비 (SD 명의 계정 권장 — 데이터 소유권 명확화) |

> 단계 단위 계약을 제안하는 이유: **MVP에서 보호자가 안 쓰면 그다음을 안 하는 게 맞습니다.**
> 전체를 한 번에 계약하면 원장님이 위험을 다 집니다. 게이트 숫자를 보고 결정하시는 것이 안전합니다.

## 7. 성과 지표 (KPI)

이 사업이 되고 있는지 판단할 숫자입니다.

| 구분 | 지표 | MVP 출시 시 | 1년 목표 |
|---|---|---|---|
| **보호자** ★ | **앱 가입률** (진료 환자 대비) | 70% | 90% |
| | **회차 리포트 열람률** ★ | 80% | 90% |
| | 입원 일일 리포트 열람률 | 90% | 95% |
| | 마지막 진료 30일 후 앱 유지율 | 50% | 60% |
| | 재방문율 (12개월 내) | — | 40% |
| **운영** | **입력 지속률** (회차·입원 중 리포트 발송 비율) ★ | 90% | 90% |
| | 입원 관련 전화 문의 | 30% 감소 | 50% 감소 |
| **레퍼** | 뷰어 계정 온보딩 병원 수 | 10곳 | 40곳 |
| | 월 신규 의뢰 건수 | 기준선 유지 | **+30% 이상** |
| | 의뢰 → 실제 진료 전환율 | 70% | 80% |
| **이후 단계** | PACS 도입 / 첫 의뢰 신규 병원 / EMR 전환 | — | 게이트 통과 후 설정 |

**가장 중요한 두 지표**
1. **회차 리포트 열람률** — 보호자가 실제로 보는가. 이게 낮으면 모든 게 무의미합니다.
   *(모든 진료에 발생하는 리포트라 표본이 가장 크고, 앱의 생존을 가장 정확히 보여줍니다.)*
2. **입력 지속률** — 의료진이 계속 넣고 있는가. **이게 떨어지면 1번도 같이 떨어집니다.**
   수기 입력을 전제로 시작하므로, 이 숫자를 매주 봅니다.

## 8. 기술 개요

| 영역 | 선택 | 이유 |
|---|---|---|
| 웹/앱 | Next.js (App Router) | EMR·포털·앱을 한 코드베이스로 → 개발·유지보수 비용 절감 |
| DB / 인증 | Supabase (PostgreSQL) | **RLS로 권한을 DB에서 강제** — 의료정보 유출 원천 차단 |
| 파일 저장 | 오브젝트 스토리지 (S3 호환) | 영상·CT·MRI 대용량. 저장 비용 최적화 및 이관 자유 |
| DICOM | 표준 C-STORE 수신 + 웹 뷰어 | 장비 제조사 무관 연동 |
| 보호자 앱 | PWA → 네이티브 래핑 | 초기 검증 속도, 이후 스토어 출시 |
| AI | 상용 판독 API 연동 → 자체 모델 | 초기 리스크 최소화 |
| 배포 | 클라우드 (국내 리전) | 개인정보 국내 보관 |

**핵심 설계 원칙 — 권한은 앱이 아니라 DB에서 막는다.**
"1차 병원은 자기가 의뢰한 환자만", "보호자는 자기 반려동물만" 이라는 규칙을 앱 코드로만 지키면
버그 하나로 타인의 의료정보가 노출됩니다. 이 플랫폼은 그 규칙을 데이터베이스 자체에 심어
**앱에 버그가 있어도 데이터가 새지 않게** 설계되어 있습니다. *(현재 SD EMR에 적용·검증 완료)*

## 9. 다음 단계

### 원장님께 여쭐 것

1. **입원 병동 동선** ★ — 하루 중 언제, 누가 입원 환자를 보는지. **입력 화면은 그 동선 위에 얹혀야 합니다.** 저희가 반나절 참관하는 것이 가장 정확합니다.
2. **입력 담당** — 리포트를 수의사가 직접 넣을지, 테크니션이 넣고 수의사가 확인만 할지. 화면 설계가 달라집니다.
3. **파일럿 1차 병원 5~10곳** — 이미 자주 의뢰해 주시는 병원. 뷰어 계정을 먼저 열어 드립니다.
4. **의뢰 건수 기준선** ★ — 최근 6~12개월 병원별 의뢰 건수. **게이트 판정의 전제이며, 지금 확보하지 않으면 나중에 복원이 어렵습니다.**
5. **보호자 앱 톤** — SD 브랜드 색·로고·말투. 완성도에 힘을 싣기로 한 만큼 여기서 결정이 필요합니다.
6. **범위 확정** → 상세 견적서 및 계약서 제출

*영상 장비 목록·DICOM 연동·세그먼트 B 영업 인력은 **게이트 통과 후**에 여쭙겠습니다. MVP에는 필요 없습니다.*

### 당사가 준비할 것

- **보호자 앱 화면 설계 + 디자인 시안** (가장 먼저)
- **입원 병동 참관 → 입력 화면 설계 + 프로토타입** — 실제 병동에서 8마리 5분 안에 되는지 그 자리에서 시연·검증
- MVP 상세 기능 명세
- 파일럿 병원 인터뷰 (당사 동행 가능)
- 법률 자문 항목 정리 (4.2 표 기준)
- Phase 1 견적서

### 부록 — 현재 구축 상태

Phase 0(SD 본원 EMR)은 **개발 완료되어 동작 중**이고, MVP도 상당 부분 올라가 있습니다.
데모 접속으로 직접 확인하실 수 있는 것:

- 환자 관리 / 진료 기록 / 처방 / 영상 업로드 / 입원 바이털 그래프
- **오늘 할 일** + 병동 입력 화면 (카메라 즉시 · 바이털 프리필 · 한 화면 발송)
- **보호자 리포트 + 전송 미리보기** · 지난 방문 대비 변화 · 종합 리포트(PDF)
- **전자 동의서** (양식 5종 · 서명 · 주민번호 암호화)
- 1차 병원 원장용 화면 (진행 상태 · 환송 소견서) · **레퍼 대시보드** · 접근 로그
- 보호자 모바일 앱 (PWA — 홈 화면에 설치됩니다)

데모 데이터에는 **환자 12명의 3~8년치 진료 이력(236회차)** 이 들어 있어,
장기 환자의 체중 변화와 병원별 의뢰 추이가 실제처럼 보입니다.

**알림까지 붙어 있습니다.** 리포트를 보내면 보호자 휴대폰에, 입원·퇴원·환송 시 원장님 휴대폰에
바로 알림이 갑니다. 문자가 아니라 앱 알림이라 **발신번호 등록도, 건당 요금도 없습니다.**

지금 남은 것은 **재료 두 가지**입니다 — 맞춤 질문·답변에 쓸 **10년치 상담 기록**, 건강검진 리포트 **샘플**.

**이 기획서는 "만들겠습니다"가 아니라 "여기까지 만들었고, 여기서 이렇게 확장하겠습니다"입니다.**
