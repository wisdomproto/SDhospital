⚠️ **원본은 저장소에 넣지 않는다.** 보호자 이름·전화번호가 평문으로 들어 있다. 집계와 결론만 남긴다.

## 범위 (2026-08-03 확정)

- **예약 → 전화 상담으로 연결한다.** 자동으로 잡지 않는다.

## 설계

### 자동답변이 해야 하는 일

데이터가 말하는 답은 세 갈래뿐이다 — **지금 오세요 / 아침에 오세요 / 이렇게 해보세요**.
원격으로 끝나는 3%를 늘리려 하면 안 된다. 그건 진료다.

```
증상 메시지
  │
  ├ ① 지금 와야 하는 것        발작·경련 / 호흡곤란 / 배뇨 못 함 / 다량 출혈 /
  │                            수술 부위 벌어짐·출혈 / 의식 저하
  │                            → "지금 오세요" + 야간 안내 + 전화 연결
  │
  ├ ② 아침에 와야 하는 것      3일 이상 안 먹음 / 반복 구토 / 혈변 / 절뚝임 지속
  │                            → "내일 오전 예약 잡아드릴게요" + 그때까지 볼 것
  │
  └ ③ 물어볼 것부터 채우는 것  피부 붉어짐 · 실밥 부위 · 눈곱 …
                               → 사진 요청 + 언제부터·횟수·먹는 약 물어보고
                                 **주치의에게 넘긴다**(사람이 답한다)
```

**①만이라도 밤에 즉시 나가면 지금보다 낫다.** 지금은 그 자리에 "안 합니다"가 나간다.

### 지켜야 할 선

- **진단하지 않는다.** 병명을 말하지 않는다. `~일 수 있습니다` 도 하지 않는다.
- **안심시키지 않는다.** "괜찮아요"는 사람만 한다 — 실제로도 10%뿐이고 그마저 주치의 확인을 거친다.
- **약을 지시하지 않는다.** 중단·투여 모두. 실제 조치 지시 13%는 넥카라·급여 중단 같은 것이고 주치의 판단이었다.
- **①은 넓게 잡는다.** 놓치는 쪽이 과하게 부르는 쪽보다 훨씬 나쁘다.
- 답변 끝에는 항상 **"의료진 확인 전 자동 안내"** 라고 밝힌다.

### 사람에게 넘길 때

③으로 분류된 건 **직원 화면의 "오늘 할 일"에 올린다.** 지금 리포트가 그러는 것과 같다.
답장 초안은 AI 가 만들되 **발송은 사람이 누를 때만** — 입원 리포트의 `ready_at`/`sent_at` 과 같은 구조다.
이러면 44%의 "주치의 확인 후" 왕복이 한 번으로 줄고, 물어볼 것(사진·시점·횟수)은 이미 채워져 있다.

## 기록을 보고 답한다 — 이게 지식인과 다른 점

같은 "밥을 안 먹어요"도 **어제 수술한 아이 · 항암 3차 중인 아이 · 3년째 건강하던 아이**가 전부 다른 문제다.
우리는 그 셋을 구분할 수 있는 유일한 쪽이다 — **기록이 우리한테 있다.**
답변을 만들기 전에 이 아이의 상태를 먼저 읽는다.

| 읽는 것 | 어디서 | 답이 어떻게 갈리는가 |
|---|---|---|
| 최근 회차·주 증상 | `visit` | 2주 전 슬개골 수술 → "절뚝임"은 수술 부위 문제로 먼저 본다 |
| 진행 중인 입원 | `admission` | 입원 중이면 채팅이 아니라 병동에 물어야 한다 |
| 오늘까지의 입원 경과 | `admission_report` | "밥 먹었나요"는 이미 답이 있다 — 리포트로 답한다 |
| 최근 검진·수치 | `checkup` / `checkup_value` | 신장 수치가 올라와 있던 아이의 "물을 많이 마셔요"는 우선순위가 다르다 |
| 처방 | `prescription` | 스테로이드 복용 중이면 팬팅·다음다뇨는 부작용 후보다 |
| 영상 | `medical_image` (PACS) | 최근 흉부 촬영이 있으면 "기침"에 그 소견을 붙인다 |
| 의뢰 병원 | `patient.referring_hospital_id` | **아래 — 경미하면 1차 병원으로 보낸다** |

⚠️ **PACS 는 판독하지 않는다.** AI 가 영상을 읽는 게 아니라 **"최근 어떤 촬영이 있었고 소견이 무엇이었나"**를 참조한다.
영상 판독은 사람이 한다. (의료영상 뷰어·DICOM 은 아직 보류 상태다)

⚠️ **채팅이 노출 정책의 우회로가 되면 안 된다.** 보호자에게 진료 원문·처방 상세를 보여주지 않는 규칙은 그대로다.
AI 는 기록을 **읽어서 판단에 쓰되**, 보호자에게 되돌려 주는 문장에는 담당의 코멘트 수준까지만 담는다.

## 경미하면 1차 병원으로 돌려보낸다

의뢰받은 환자(`referring_hospital_id` 가 있는 환자)가 **경미한 증상**으로 물어오면,
우리 병원이 아니라 **의뢰한 1차 병원으로 안내한다.**

```
증상 접수 → 기록 조회 → 중증도
   ├ 응급        → 지금 우리 병원으로 (야간 안내 + 전화 연결)
   ├ 중등도       → 우리 병원 예약
   └ 경미 + 의뢰 환자 → "○○동물병원에서 보시는 게 빠릅니다"
                        + 1차 병원에 상황 전달
                        + [그래도 저희 병원으로 갈게요] 를 **항상 같이 둔다**
```

**왜 우리 매출을 남에게 넘기는가.** 이 앱의 목적은 우리 병원 예약을 늘리는 게 아니라
**1차 병원이 안심하고 의뢰하게 만드는 것**이다. 2차 병원이 환자를 가져가 버린다는 의심이 있으면 의뢰가 끊긴다.
경미한 건을 돌려보내는 것이 **의뢰가 계속 들어오게 하는 값**이고, 그게 우리가 만드는 유통망의 본체다.

**지켜야 할 것 셋**

1. **경미 판정은 보수적으로.** 틀려서 1차 병원으로 보낸 아이가 잘못되면 그건 우리 사고다.
   조금이라도 애매하면 경미로 내리지 않는다. **1차 병원 안내에도 반드시 조건을 붙인다** —
   "이런 변화가 보이면 저희로 바로 오세요"가 없는 안내는 내보내지 않는다.
2. **1차 병원이 먼저 알아야 한다.** 보호자만 보내면 1차 병원은 모르고 있다가 받는다.
   `/referral` 포털에 **"우리가 의뢰했던 ○○가 이런 증상으로 갈 예정"** 을 띄우고 푸시한다.
   이게 실제로 관계를 만드는 장치다 — 보호자를 돌려보낸 것보다 **알려준 것**이 기억에 남는다.
3. **보호자의 선택을 막지 않는다.** "그래도 저희 병원으로 오시겠어요?" 는 **항상 열려 있어야 한다.**
   앱이 자기를 거절했다고 느끼는 순간 그 보호자는 앱을 지운다. 안내는 권유지 차단이 아니다.

**경미로 볼 수 있는 것 (원장님 확정 필요)** — 단순 외이염·가벼운 피부 트러블·1회성 구토/설사로 활력이 정상·
발톱/항문낭·접종 문의. **경미로 절대 내리지 않을 것** — 우리가 수술한 부위 문제·우리가 처방한 약 관련·
진행 중인 질환(항암·신장·심장)의 증상 변화. 이건 의뢰 환자여도 **우리가 본다.**

## 두 갈래로 나눈다 — 입원 전후 / 일반 증상

표본에서 증상 문의의 **83%가 입원·수술 전후 맥락**이었다(전후 3일 안에 입원·수술 언급이 있는 것).
같은 "밥을 안 먹어요"도 입원 중이면 **기록 조회**고, 집에 있는 아이면 **증상 분류**다.
하나의 흐름으로 처리하면 둘 다 못 한다.

### ① 입원·수술 전후 — **확정**

- 오늘 식사·배변·경과는 **이미 리포트에 있다.** 그걸로 답한다.
- 수술 후 관리(실밥·발적·소독)는 답이 정형적이라 자동답변이 가장 잘 듣는다.
- ⚠️ **채팅 내용을 그대로 담당의에게 전달한다.** 자동답변이 무엇을 답했든 주치의가 그 대화를 본다.
  입원 중인 아이의 말은 전부 진료 정보다.

### ② 일반 증상 — **답이 먼저, 안내가 그다음**

**제일 먼저 하는 건 그 증상에 대한 교과서적 답변이다.** 분류부터 하면 안 된다 —
보호자가 밤에 원하는 건 안내가 아니라 **설명**이다.

```
"켁켁거리는 게 너무 심해요"
  → ① 움직일 때 심해지는 켁켁거림은 기관 허탈에서 흔한 형태입니다.
       목줄 대신 하네스를 쓰시고 흥분·더운 환경을 피해 주세요.   ← 먼저
  → ② 혀가 파래지거나 쓰러지면 지금 오세요 / 아니면 내일 오전     ← 그다음
```

답을 주기에 정보가 부족하면 그때 **문진**(사진·언제부터·횟수·복용 약)을 먼저 받는다.

**안내처는 넷이다** — 지금 우리 병원 · 우리 병원 예약 · **1차 병원** · 담당의 확인 후.
1차 병원은 곁가지가 아니라 **넷 중 하나의 정식 출구**다.

그다음 **이어서 누가 답하느냐**가 미결정이다.

| 안 | 깨지는 지점 |
|---|---|
| A 우리 의료진 | 확장하면 반드시 깨진다. 지금도 44%가 "주치의 확인 후"다 |
| B 1차 병원 담당의 | 회송 논리와 맞는다. **그쪽 의향을 모른다 — 먼저 물어야 한다** |
| C 채팅 전담 인력 | 인건비가 환자 수를 따라 늘고 야간은 여전히 공백 |
| **D AI 초안 + 사람 검수** | 이 기획의 기본안. 물량이 늘어도 사람이 안 는다. **검수는 누가 하나**가 남는다 |
| E 답하지 않고 예약만 | 무한히 확장되지만 지금 자동응답과 크게 다르지 않다 |

⚠️ **83:17 은 오늘의 환자 구성이지 앞으로의 비율이 아니다.**
이 표본은 **이미 우리 병원에 입원·수술한 환자**들의 채널이다. 1차 병원을 늘리고 그곳 환자가 앱을 쓰기 시작하면
그 아이들은 입원한 적이 없다 — **일반 증상이 주력이 된다.** 지금 비율로 이 갈래를 작게 설계하면 안 된다.

**한 가지 관점**: 1차 병원 환자가 늘수록 B가 자연스러워진다. 그 아이의 주치의는 1차 병원이고 일반 증상은 원래 그쪽 몫이다.
그러면 우리 채팅의 역할은 답을 주는 게 아니라 **"1차 병원으로 잘 보내주는 것"**이 되고, 그게 플랫폼이 하려는 일과 맞는다.
다만 **응급 분류만은 우리가 한다** — 1차 병원은 밤에 안 열려 있고, 넘겼다가 늦으면 책임은 앱을 만든 쪽에 온다.

## 만드는 순서

| | 무엇 | 왜 |
|---|---|---|
| **C-1** | **응급 분류(①) + 야간 즉시 안내** | 지금 "안 합니다"가 나가는 자리. 규칙만으로 된다 |
| **C-2** | **문진 채우기(③)** — 사진·시점·횟수·복용 약 | 왕복 44%를 한 번으로 줄인다 |
| **C-3** | **직원 화면 인계 + 답장 초안** | 발송은 사람. 기존 구조 재사용 |
| **C-4** | **수술 부위 전용 흐름** | 문의 4위(29건)인데 답이 정형적이다 — 사진 + 며칠째 + 벌어짐 여부 |
| **C-5** | **기록 연계** — 최근 회차·입원·검진·처방·영상을 읽고 답을 가른다 | 지식인과 갈리는 지점. 데이터는 이미 우리 DB 안에 있다 |
| **C-6** | **1차 병원 회송** — 경미 + 의뢰 환자 → 1차 병원 안내 + 그쪽에 알림 | 의뢰가 계속 들어오게 하는 값 |
| **C-7** | 예약 요청은 **전화 연결**로 | 자동으로 안 잡는다 |

C-1·C-2 는 **모델이 필요 없다.** 증상 키워드와 규칙이다.
모델은 C-3 초안에서 처음 필요하고, 그때도 보호자가 아니라 **직원에게** 말한다.
C-5 는 **EMR 조회**지 판독이 아니다 — 붙일 데이터가 전부 이 코드베이스 안에 있어서 연동이랄 것도 없다.

## 다음에 확인할 것

- **1만 건 전체를 받으면 다시 센다.** 105건은 표본이고, 특히 ①(응급)이 34건뿐이라 분류 규칙을 세우기엔 얇다.
  전체에서 **응급으로 판명난 사례**를 뽑아야 "지금 오세요" 기준을 사람 손으로 정할 수 있다.
- **비식별화가 먼저다.** 이름·전화번호가 평문이다.
- 야간 응급 안내 문구와 ① 목록은 **원장님이 직접 확정해야 한다.** 우리가 정할 것이 아니다.
- **경미 목록도 원장님이 확정해야 한다.** 1차 병원으로 돌려보내는 기준이라 우리가 정하면 안 된다.
- **1차 병원이 이 알림을 반길지 확인해야 한다.** "환자 갑니다"가 도움으로 읽힐지, 통보로 읽힐지는
  원장님들 반응을 봐야 안다. 애니컴·아이원 두 곳에 먼저 물어보는 게 낫다.
- **회송했다가 되돌아온 사례를 세야 한다.** 경미 판정이 맞았는지는 그 숫자로만 검증된다.
  1차 병원 갔다가 다시 우리한테 온 비율이 높으면 기준을 조인다.
